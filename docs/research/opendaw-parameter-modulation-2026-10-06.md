# openDAW parameter modulation, 2026-10-06

This records the source audit before implementation. For the resulting Radio
prototype and its runtime boundaries, read the
[modulation contract](../../apps/radio/src/components/radio/node/docs/modulation.md).

## Finding and version scope

openDAW already provides **four reusable, project-wide parameter-modulation sources: LFO, Steps, Random, and Macro**. They are native engine features, exposed through `project.api.modulation`; the [kind registry](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/adapters/src/modulation/Modulators.ts) and [project API](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/core/src/project/ProjectModulation.ts) enumerate them explicitly.

Radio's [package manifest](../../apps/radio/package.json) and [lockfile](../../bun.lock) pin `studio-core` 0.2.7, `studio-adapters` 0.3.5, `studio-boxes` 0.0.111, `lib-dsp` 0.0.94, and `studio-core-wasm` 0.0.18. Inspection of the published core/adapters/boxes tarballs confirmed the four creators, assignments, adapter controls, and schemas at those versions. Their package metadata identifies source commit `88113f892cea2fa9495289a9c166b6fe0f93ce69`. **A package upgrade is not required to expose these four sources.** Registry provenance: [core 0.2.7](https://registry.npmjs.org/@opendaw/studio-core/0.2.7), [adapters 0.3.5](https://registry.npmjs.org/@opendaw/studio-adapters/0.3.5), [boxes 0.0.111](https://registry.npmjs.org/@opendaw/studio-boxes/0.0.111).

Latest upstream was independently checked at `52408ea0f62236bc9084aa4c73f156c163570da7`, dated October 2, 2026. Links below freeze that snapshot. Package presence and current upstream behavior were inspected; audible behavior in Radio was not tested.

The use cases are recommendations inferred from each source's controls, not additional built-in preset types.

Timed sources share sync choices **Off, 8/4/2/1 bars, 1/2, 1/4, 1/6, 1/8, 1/12, 1/16, 1/24, 1/32**, plus free rate **0–10 Hz**. Sync and free frequencies add; they are not mutually exclusive modes. They continue while transport is stopped. Upstream engine re-anchors on pause/resume, locate, and loop jumps; no note-trigger/reset input appears in these global schemas. The manual contains conflicting wording about loop re-phasing, so the engine is the authority for that detail. [Rate definitions](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/adapters/src/modulation/LfoModulatorBoxAdapter.ts), [engine clock](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/crates/engine/src/lib.rs#L2008).

## Shared routing and existing UX

Each source has its own enable flag, 0–100% Range, and bipolar/unipolar polarity. An assignment has an independent enable flag and signed depth. One source can drive many targets; several sources can drive one parameter. Contributions add in normalized parameter space over the stored value or automation, then clamp to 0–1. The authored base value remains separate from the live result. Targets include device controls, mixer controls, sends, and MIDI CC parameters. [Shared schema](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/forge-boxes/src/schema/std/modulators/ModulatorFactory.ts), [assignment schema](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/forge-boxes/src/schema/std/ModulationBox.ts), [parameter resolution](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/adapters/src/AutomatableParameterFieldAdapter.ts).

openDAW's own [assignment menu](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/app/studio/src/ui/menu/automation.ts) already provides **right-click parameter → Modulate → New/existing source**. Creating a source reveals it in the dedicated Modulation screen. Its [target list](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/app/studio/src/ui/modulation/TargetList.tsx) provides target names, owner navigation, depth, enable, and removal. Live parameter readouts and control-source indicators show the effective movement. These are useful references for prototypes; Radio uses its own React UI and does not currently embed that studio screen. [Manual](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/app/manual/public/modulation.md), [knob feedback](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/app/studio/src/ui/components/Knob.tsx).

Automation and MIDI learn also drive modulator controls and assignment depths. A second modulator can modulate **an assignment's depth**, enabling movement of modulation strength. The sources' own rate/shape/range controls accept automation and MIDI, but exclude modulation: a cable from LFO to another global LFO's rate is not a native supported connection. Pattern count/direction and Random seed/loop/levels are ordinary fields, rather than automatable parameters. [Pointer rules](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/forge-boxes/src/schema/std/Defaults.ts), schemas linked above.

## Related capabilities and limits

The four-kind registry contains **no global envelope follower, ADSR/MSEG, XY pad, keytracking, or velocity modulator**. Gate and Vocoder have internal envelope followers; Vaporisateur has internal LFO/envelope destinations. Those cannot be presented as reusable arbitrary-parameter sources. Tidal is a native tremolo/auto-pan effect, useful if amplitude/panning movement alone is desired. [Gate](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/app/manual/public/devices/audio/gate.md), [Vocoder](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/app/manual/public/devices/audio/vocoder.md), [Vaporisateur](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/app/manual/public/devices/instruments/vaporisateur.md), [Tidal](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/app/manual/public/devices/audio/tidal.md).

The separate Modular subsystem has audio input/output, gain, delay, and multiplier modules, using `VoltageConnection`. Its registry provides neither LFO/follower modules nor an external arbitrary-parameter modulation bridge. [Module registry](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/forge-boxes/src/schema/std/modular/index.ts), [connection schema](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/forge-boxes/src/schema/std/modular/modules.ts).

## Further candidates beyond the four global kinds

The follow-up audit found useful native building blocks and device-local sources, **not additional registered global kinds**. The pinned `lib-dsp` 0.0.94 exports `Adsr`, `RMS`, `Smooth`, `Ramp`, `FadingEnvelope`, and `TidalComputer`. Instrument adapters also include Vaporisateur, Tubular, Neon, and Cubed. Latest upstream HEAD remains the October 2 snapshot above. [DSP exports](https://github.com/andremichelle/openDAW/blob/88113f892cea2fa9495289a9c166b6fe0f93ce69/packages/lib/dsp/src/index.ts), [published adapters package](https://registry.npmjs.org/@opendaw/studio-adapters/-/studio-adapters-0.3.5.tgz).

| Candidate for Node mode | Existing openDAW support | What still needs building |
| --- | --- | --- |
| **Audio envelope follower** | Exported `RMS` measures level; `Smooth` smooths a signal. Gate/Vocoder already contain peak/attack-release detection. | Audio tap, sensitivity/range/ballistics, and control-output bridge. Strong fit for one station's loudness moving another parameter. No standalone follower source. [RMS](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/lib/dsp/src/rms.ts), [Gate detector](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/crates/stock-devices/device-gate/src/lib.rs). |
| **Triggered ADSR envelope** | Exported `Adsr` supports gate-on/off and sample-buffer processing; Vaporisateur uses it. | Trigger input and output bridge. Could turn a button or MIDI note into a parameter swell/decay. [ADSR](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/lib/dsp/src/adsr.ts). |
| **Drawn curve / envelope sequencer** | Native value automation supports steps, linear interpolation, shaped curves, regions and clips; it can target a Macro value. | Node editor/transport integration. Existing automation is ready to drive official targets, but pauses with the song; a freely running or triggerable MSEG is a new source adapter. [Automation guide](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/scripting/docs/guide/05-automation-and-modulation.md), [interpolation](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/adapters/src/timeline/event/InterpolationFieldAdapter.ts). |
| **Slew / smoothing** | `Smooth` is a one-pole smoother; `Ramp.linear` moves toward a target over a chosen duration. | Control-node adapter. Useful for softening MIDI, Macro, or stepped changes; it transforms a source rather than generating one. [Smooth](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/lib/dsp/src/smooth.ts), [Ramp](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/lib/dsp/src/ramp.ts). |
| **Tidal-shaped LFO** | Exported `TidalComputer` computes a phase-driven shape with depth, slope and symmetry. | Clock and target bridge to make its asymmetric/pumping shapes drive arbitrary parameters. The existing Tidal device itself already performs tremolo/auto-pan. [Shape computer](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/lib/dsp/src/tidal.ts). |
| **MIDI CC / mod-wheel Macro** | MIDI learn maps CC messages directly to parameter inputs; CC1 can drive the native Macro and its assignments. | Radio mapping UI/integration. This is a ready native control path, not another global kind; pitch-bend/aftertouch mapping is not supported by this learn path. [MIDI learning](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/core/src/midi/MIDILearning.ts). |
| **Euclidean rhythm / note-derived control** | A bundled project script has a Euclidean helper; Arpeggio and Velocity generate/transform notes. | A Euclidean pattern can populate existing Steps; note-to-gate/velocity/keytracking control needs an adapter and a policy for simultaneous notes. These are not global parameter sources. [Euclidean example](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/app/studio/src/ui/pages/code-editor/examples/acid.ts), [Arpeggio](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/app/manual/public/devices/midi/arpeggio.md), [keyboard tracking](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/lib/dsp/src/midi-keys.ts). |

**Synth-local precedents:** Neon has six 8-stage envelopes with sustain/end markers and one-shot operation. Tubular has four-stage operator/pitch envelopes and an LFO with sample-and-hold, key sync, and delayed fade-in. Vaporisateur has ADSR, note velocity, keyboard tracking, and fixed LFO destinations. Cubed's accent/slide/decay/random pattern generation is local to its acid voice. These supply design/code references, not routable source outputs. Tubular's manual mentions modulation wheel, but its engine controller state leaves that path neutral; it should not be advertised as working wheel input. [Neon envelopes](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/crates/stock-devices/device-neon/src/envelope.rs), [Tubular](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/app/manual/public/devices/instruments/tubular.md), [controller limitation](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/crates/stock-devices/device-tubular/src/note.rs#L101), [Vaporisateur voice](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/crates/stock-devices/device-vaporisateur/src/voice.rs), [Cubed](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/app/manual/public/devices/instruments/cubed.md).

**Scriptable devices do not fill the missing output bridge:** Spielwerk yields validated notes, not CCs or generic parameter values. Apparat generates stereo audio; Werkstatt transforms stereo audio. Their declared parameter knobs receive controls; they do not expose a modulator-output contract. A custom script modulator would therefore require new integration. MIDIOutput sends CCs/clock to external hardware, not internal arbitrary parameters. [Spielwerk contract](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/core-wasm/src/script-spielwerk.ts), [audio/script bridge](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/studio/core-wasm/src/script-bridge.ts), [MIDIOutput](https://github.com/andremichelle/openDAW/blob/52408ea0f62236bc9084aa4c73f156c163570da7/packages/app/manual/public/devices/instruments/midioutput.md).

For Radio, the strongest further choices are **Follower, triggered Envelope, drawn Curve, Slew, and Tidal-shaped LFO**, with **MIDI CC → Macro** as the existing direct control path. This prioritization is an inference from Radio's live-audio use case.

## Radio integration implication and validation at audit time

Radio's [node catalogue](../../apps/radio/src/lib/node-graph/catalogue.ts) marks LFO/Macro/Randomiser/Follower/Clock and parameter control ports as unshipped v2; its [compiler](../../apps/radio/src/lib/node-graph/compile.ts) has no modulation lowering. The [official runtime](../../apps/radio/src/lib/audio/manager/official-opendaw-runtime.ts) edits authored box fields during reconciliation. The [roadmap](../../apps/radio/src/components/radio/node/docs/roadmap.md) requires a transient modulation path preserving base values. Native assignments fit that requirement for official box-backed parameters. Radio's [Web Audio Gain/Pan/Filter and source volume](../../apps/radio/src/lib/audio/manager/audio-manager-types.ts), plus compatibility FX, need their own target bridge; native openDAW assignments do not automatically reach them. Custom follower/XY/trigger behavior also needs additional work. This is an integration inference, not an implemented feature.

Only this research note was added. Verified repository paths, upstream snapshot, pinned package exports/schemas, and first-party source links. No build, typecheck, or test run: documentation-only evaluation, with no runtime change or audible prototype.
