# Radio metadata update mechanisms, 2026-09-24

The ten default stations in [`const.ts`](../../apps/radio/src/lib/const.ts) use seven provider types. I checked the provider code, the providers' public responses on September 24, 2026, and the available first-party platform documentation. The live observations below are snapshots, not a promise that a field is always populated.

Before this change, the [client hook](../../apps/radio/src/lib/hooks/use-radio-metadata.ts) polled every 30 seconds while playing. The [server cache](../../apps/radio/src/lib/metadata/cache.ts) and [retrieval path](../../apps/radio/src/lib/metadata/retrieval.ts) gave successful live snapshots a fixed 15-minute lifetime. The browser therefore often requested an unchanged snapshot 30 times, while a real programme change could remain hidden until that snapshot expired.

## Finding

I found no documented, public SSE, WebSocket, or GraphQL subscription feed for these ten stations. That is a limit of this investigation, not proof that none exists. Their **existing HTTP responses already carry useful change boundaries**. The practical improvement is to fetch a bounded schedule, retain the current and next programme locally, and refresh near the relevant end time with a periodic check for schedule edits or live overrides. A permanent subscription to the audio stream would carry mostly a short title and would require a continuous connection; it would not replace the episode artwork, description, and link lookups supplied by the programme APIs. [Airtime's API documentation](https://help.sourcefabric.org/hc/en-us/articles/115000382243-Airtime-Pro-API) describes HTTP live and schedule responses, including current and next track/show times. [Icecast's server statistics documentation](https://icecast.org/docs/icecast-2.4.1/server-stats.html) describes stream title as source-provided metadata.

Keep a capped refresh for unscheduled changes and use validators when applicable. |

## Design consequence

Treat the programme/episode as the cache identity, not each metadata request. For the Airtime stations, LYL, NTS, HKCR, and Alhara, use the provider's existing boundary fields to schedule the next check, with an upper bound for edits and a small delay after the boundary for provider/CDN propagation. Fetch rich details only when the identity changes. NTS should be fetched once for both channels. These are recommendations inferred from the observed response fields, not provider-prescribed polling intervals.

ICY metadata can still help when a provider API fails. Icecast's [configuration guide](https://icecast.org/docs/icecast-trunk/config_file/) describes periodic metadata insertion into compatible streams, and its [server statistics guide](https://icecast.org/docs/icecast-2.4.1/server-stats.html) identifies the title as source-set metadata. I found no evidence that a long-lived stream connection would supply the rich programme information for these stations. Keeping ten permanent upstream connections solely to learn about occasional hour-long item changes would need an operational justification that the current APIs do not yet show.
