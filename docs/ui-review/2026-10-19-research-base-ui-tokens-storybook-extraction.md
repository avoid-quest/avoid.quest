## A. Radix → Base UI through shadcn

### Selection, configuration, and generated output

**Base UI is an official shadcn primitive option.** Initialization accepts `--base base`; the persistent choice is encoded in `components.json`’s **`style`**, such as `base-nova`. There is no separate `"base": "base"` field in the current schema, and an `@base` registry namespace is unnecessary. `--preset` selects a broader preset; it is not a separate runtime dependency switch. [CLI documentation](https://ui.shadcn.com/docs/cli), [current configuration schema](https://ui.shadcn.com/schema.json).

For a **new staging workspace**, after creating its package and TypeScript configuration:

```bash
bunx --bun shadcn@4.22.1 init \
  --cwd packages/ui-base \
  --base base \
  --preset nova

bunx --bun shadcn@4.22.1 add button select dialog slider \
  --cwd packages/ui-base
```

For this package, the corresponding configuration shape is:

```json
{
  "$schema": "https://ui.shadcn.com/schema.json",
  "style": "base-nova",
  "rsc": true,
  "tsx": true,
  "tailwind": {
    "config": "",
    "css": "src/styles/globals.css",
    "baseColor": "neutral",
    "cssVariables": true,
    "prefix": ""
  },
  "iconLibrary": "lucide",
  "aliases": {
    "components": "@avoid.quest/ui/components",
    "utils": "@avoid.quest/ui/lib/utils",
    "hooks": "@avoid.quest/ui/hooks",
    "lib": "@avoid.quest/ui/lib",
    "ui": "@avoid.quest/ui/components"
  }
}
```

This preserves the repository’s existing aliases and `rsc` setting. `rsc: true` controls generated client directives; it does not make TanStack Start or Astro use React Server Components. Consumer `components.json` files should agree on style, icon library, and base color. [Official monorepo configuration](https://ui.shadcn.com/docs/monorepo).

**Existing projects can migrate without reinitialization.** Changing `style` affects subsequent additions; it does not rewrite installed components or their consumers. Furthermore, **`new-york` has no `base-new-york` counterpart**. Replacing it with `base-nova` and overwriting components combines a primitive migration with a visual redesign. The official migration guidance explicitly distinguishes this legacy-style case. [Official migration skill](https://github.com/shadcn-ui/ui/blob/main/skills/migrate-radix-to-base/SKILL.md).

Today, `bunx --bun shadcn@latest add …` in a Base-configured project generates owned TSX wrappers:

- Imports from `@base-ui/react/<component>`.
- Base UI anatomy and props beneath familiar shadcn wrapper names.
- Tailwind classes, `data-slot` hooks, and current state selectors.
- Current registry components commonly import `cn` from the **`cn` package**, rather than the older local `clsx`/`tailwind-merge` helper.
- Registry placeholders are resolved to the configured icons and aliases by the CLI. Raw registry JSON is therefore an input template, not always directly compilable application code. [Manual installation](https://ui.shadcn.com/docs/installation/manual), [Select registry source](https://ui.shadcn.com/r/styles/base-nova/select.json).

**UNVERIFIED:** I inspected registry templates and CLI documentation, but did not execute initialization or generation. Exact generated bytes in this repository remain unverified.

### Concrete API mapping

These are primitive-level changes. Your wrappers can preserve selected old public props through explicit adapters.

| Area | Radix → Base UI mapping | Consumer impact |
|---|---|---|
| Composition | `asChild` → `render={<Element />}` or render callback | Move the composed element into `render`; forward props/ref. A button rendered as a link may need `nativeButton={false}`. |
| Slot | Radix `Slot` → `useRender` + `mergeProps` | Use the actual Base UI Button primitive for buttons; reserve `useRender` for custom polymorphic components. [useRender](https://base-ui.com/react/utils/use-render) |
| Dialog anatomy | `Content` → `Popup`; `Overlay` → `Backdrop` | Typical structure: `Root > Portal > Backdrop + Popup`. Your public `DialogContent` name can remain. [Dialog](https://base-ui.com/react/components/dialog) |
| Controlled overlays | `open`, `defaultOpen`, `onOpenChange` remain | Callback becomes `(open, eventDetails)`; cancellation/reason handling differs. |
| Focus | `onOpenAutoFocus` / `onCloseAutoFocus` → `initialFocus` / `finalFocus` | Accept booleans, refs, or functions. Defaults depend on interaction type; touch opening avoids automatically focusing an input. Preserve the repository’s custom return-focus behavior deliberately. [Dialog API](https://base-ui.com/react/components/dialog) |
| Outside/Escape handling | Individual Radix cancellation callbacks → Base UI change details and component-specific APIs | Audit by component; do not mechanically pass old event callbacks through. |
| Popover positioning | Positioning props move to `Positioner`; content becomes `Popup` | Structure: `Portal > Positioner > Popup`. Forward `side`, `align`, offsets, collision settings to the Positioner. [Popover](https://base-ui.com/react/components/popover) |
| Select anatomy | `Content/Viewport` → `Positioner/Popup/List` | `position="popper"` corresponds to `alignItemWithTrigger={false}` on Positioner. |
| Select value | String-only assumptions → generic values, with `null` for an empty single select | `onValueChange(value, eventDetails)` may supply `null`; audit `setState<string>` handlers. |
| Select labels / placeholder | Supply `items` metadata or an explicit value renderer where needed | `Select.Value placeholder` **exists in 1.9**. Children or a null item’s label override it. Use metadata to avoid initially showing raw IDs before popup items mount. |
| Select item value | Supply a unique explicit value for ordinary options | **Correction:** `Select.Item.value` is technically optional in 1.9’s types and defaults to `null`; it is not a required TS prop. Omission is unsuitable for multiple distinct ordinary options. [Select](https://base-ui.com/react/components/select) |
| Tooltip provider | `delayDuration` → `delay` | Current provider also has `closeDelay` and **`timeout`** for instant subsequent tooltips. Do not claim the skip-delay concept disappeared entirely. [Tooltip](https://base-ui.com/react/components/tooltip) |
| Slider anatomy | `Root > Track > Range`, thumbs → `Root > Control > Track > Indicator`, thumbs | Base thumbs include native range inputs. Supply `index` for each thumb in an SSR multi-thumb slider. |
| Slider values/events | Arrays in Radix → number or array in Base | Preserve your wrapper’s array contract if desired. `onValueCommit` → **`onValueCommitted`**; both change and commit callbacks receive event details. |
| Slider spacing | `minStepsBetweenThumbs` → `minStepsBetweenValues` | Audit collision behavior, orientation, keyboard stepping, and unsupported `inverted` usage. [Slider](https://base-ui.com/react/components/slider) |
| Switch / Checkbox | `onCheckedChange` retains its name | Signature becomes `(checked: boolean, eventDetails)`. Checkbox indeterminate state is a separate `indeterminate` prop, not `checked="indeterminate"`. |
| Tabs | `Trigger` → `Tab`; `Content` → `Panel`; optional `Indicator` | Base defaults to **manual activation**. Use `Tabs.List activateOnFocus` to preserve Radix automatic activation. Indicator is optional. [Tabs](https://base-ui.com/react/components/tabs) |
| Toggle | `pressed` / `onPressedChange` retained | Callback gains event details; styling uses `data-pressed`. |
| ToggleGroup | `type="single" / "multiple"` → `multiple` boolean | Values are arrays even in single-selection mode. Items are Base `Toggle`s. `loop` → `loopFocus`. [Toggle Group](https://base-ui.com/react/components/toggle-group) |
| Accordion | `type` / `collapsible` model → array values plus `multiple` | A single expanded item is `[value]`; collapsed is `[]`. `Content` → `Panel`. [Accordion](https://base-ui.com/react/components/accordion) |
| Collapsible | `Content` → `Panel` | `open/onOpenChange` retained with event details; review panel mounting and height animation. |
| Mounting | Radix `forceMount` → component-specific `keepMounted` | Usually on an overlay Portal or disclosure/tab Panel. It is not a universal Root prop. |
| Portals | `container` remains available | Current Dialog Portal accepts an element, ShadowRoot, or ref. Theme styling must reach portaled DOM. |
| Menus | `onSelect` and old item behavior need review | Base checkbox/radio menu items do not necessarily close by default; use `closeOnClick` when preserving existing behavior. |
| DOM / refs | Some button-like Radix parts become spans/divs plus hidden inputs | Audit element-specific refs, `disabled:` selectors, focus handlers, and form integration. |

Additional migration references: [consumer-prop inventory](https://github.com/shadcn-ui/ui/blob/main/skills/migrate-radix-to-base/consumer-props.md), [overlay mappings](https://github.com/shadcn-ui/ui/blob/main/skills/migrate-radix-to-base/overlays.md), [form mappings](https://github.com/shadcn-ui/ui/blob/main/skills/migrate-radix-to-base/form-controls.md).

State selectors and CSS variables also change:

| Radix selector / variable | Base UI counterpart |
|---|---|
| `data-[state=open]`, `data-[state=closed]` | `data-open`, `data-closed` |
| `data-[state=checked]`, `data-[state=unchecked]` | `data-checked`, `data-unchecked` |
| `data-[state=indeterminate]` | `data-indeterminate` |
| Tabs `data-[state=active]` | `data-active` |
| Toggle `data-[state=on]` | `data-pressed` |
| Select item checked styling | `data-selected` |
| Some trigger open styling | `data-popup-open` |
| Orientation selectors | Often `data-horizontal` / `data-vertical`; inspect each part |
| `--radix-*-content-transform-origin` | `--transform-origin` |
| `--radix-*-content-available-height/width` | `--available-height/width` |
| `--radix-*-trigger-width/height` | `--anchor-width/height` |
| Accordion / Collapsible content height | `--accordion-panel-height` / `--collapsible-panel-height` |

Apply equivalent changes to `group-*` and `peer-*` variants. `data-side` remains a valued attribute. [Class mapping reference](https://github.com/shadcn-ui/ui/blob/main/skills/migrate-radix-to-base/class-mapping.md).

**Animations:** `tw-animate-css` can remain. Current shadcn Base templates themselves use `data-open:animate-in` and `data-closed:animate-out`. Base also supports transitions through `data-starting-style` and `data-ending-style`. Renaming selectors is necessary, but verify exit lifetimes rather than assuming every Radix animation translates automatically. In 1.9, externally controlled unmounting can require `eventDetails.preventUnmountOnClose()` before later calling an unmount action. [Animation handbook](https://base-ui.com/react/handbook/animation), [1.9 release notes](https://base-ui.com/react/overview/releases/v1-9-0).

### Ordered migration recipe

1. **Baseline and branch.**

   ```bash
   git switch -c chore/ui-base-migration
   bun run check
   bun run typecheck
   bun run --filter @avoid.quest/radio test
   bun run --filter @avoid.quest/radio build
   bun run --filter @avoid.quest/web test
   ```

   The web test already invokes its build.

2. **Record customizations before replacing wrappers.** This repository’s slider has fader variants, fine-wheel stepping, reset/snap behavior, markers, and range origins. Dialog has custom focus restoration. Knob is already independent of Radix.

3. **Install Base alongside Radix.**

   ```bash
   bun add --cwd packages/ui @base-ui/react@1.9.0
   ```

4. **Use parallel files for the actual migration**, such as `button-base.tsx` and `dialog-base.tsx`. A separate `packages/ui-base` workspace is useful as a disposable generator/reference, but avoid maintaining two complete UI libraries.

5. **Preserve `new-york` visuals while rewiring primitives.** Use Base registry output as anatomy/type guidance. Do not bulk-run `add --all --overwrite`.

6. **Migrate in dependency order:** Button/polymorphism and simple controls; disclosure components; Select/menus; overlays; custom slider. Evaluate Vaul → Base Drawer separately.

7. **Repoint consumers one component at a time**, temporarily:

   ```tsx
   import { Button } from "@avoid.quest/ui/components/button-base";
   ```

   Update call-site props and handlers simultaneously. Do not mix Radix and Base parts within the same compound component.

8. **After each family**, typecheck and run its interaction stories. Preserve existing behavior explicitly where Base defaults differ.

9. **Restore stable import paths** once all consumers of that component migrate. Remove Radix dependencies only after searching all wrappers and app code. Retaining Vaul may retain transitive Radix dependencies.

10. **Choose future generation policy:** adopt `base-nova` for future additions, or maintain a custom registry matching the retained design. Keep consumer configurations consistent.

There is now an **official migration skill**, but the CLI’s documented migration list does **not** contain a Radix-to-Base AST codemod. `shadcn migrate radix` migrates to the consolidated `radix-ui` package—it does not select Base UI. No maintained community codemod was verified sufficiently to recommend. [Official skill](https://github.com/shadcn-ui/ui/blob/main/skills/migrate-radix-to-base/SKILL.md), [CLI migrations](https://ui.shadcn.com/docs/cli).

## B. Design tokens for Tailwind v4 + shadcn

### Recommended source of truth

**For this organization, start with versioned CSS tokens in the UI package.** Keep primitive and semantic CSS variables, then expose selected values through Tailwind `@theme inline`. This is sufficient for several web repositories sharing one visual system.

Use DTCG JSON when there is a concrete need for design-tool synchronization, multiple output platforms, substantial brand/mode combinations, or machine-readable token metadata.

| Approach | Benefits | Costs |
|---|---|---|
| CSS variables + `@theme` | Native dark mode/cascade; no token build; easy package distribution; fits existing shadcn code | Less structured metadata; harder native-platform generation and design-tool round trips |
| DTCG JSON + Style Dictionary | Typed token interchange, aliases, multiple outputs, mature transformation ecosystem | Build/configuration ownership; mode and alias handling; generated-file discipline |
| DTCG JSON + Terrazzo | DTCG-focused tooling, token validation/linting, CSS and JS/TS plugins | Smaller ecosystem; assess required plugin coverage |
| Tokens Studio authoring | Designer workflow and token synchronization | Still needs an agreed transformation pipeline; its extensions may require `@tokens-studio/sd-transforms` |

DTCG **2025.10** is a published community-group specification; it should not be described as a W3C Recommendation. [DTCG format](https://www.designtokens.org/tr/2025.10/format/), [Terrazzo](https://terrazzo.app/docs/), [Tokens Studio transformation guidance](https://docs.tokens.studio/transform-tokens/style-dictionary).

### Three-tier model

Suggested naming:

| Tier | CSS examples | Responsibility |
|---|---|---|
| Primitive/reference | `--aq-ref-neutral-950`, `--aq-ref-space-2`, `--aq-ref-radius-2` | Raw palette and scales |
| Semantic/alias | Existing `--background`, `--foreground`, `--primary`, `--radius`; new `--aq-sys-control-height`, `--aq-sys-layer-overlay` | Theme-dependent roles |
| Component | `--aq-comp-slider-track-height`, `--aq-comp-button-radius` | Only values that need component-specific control |

Preserve shadcn’s public semantic names rather than replacing every `bg-primary` call site.

Illustrative CSS:

```css
:root {
  /* Reference values */
  --aq-ref-neutral-50: oklch(0.985 0 0);
  --aq-ref-neutral-950: oklch(0.145 0 0);
  --aq-ref-space-2: 0.5rem;
  --aq-ref-radius-2: 0.625rem;
  --aq-ref-duration-fast: 120ms;

  /* Semantic roles */
  --background: var(--aq-ref-neutral-50);
  --foreground: var(--aq-ref-neutral-950);
  --primary: var(--aq-ref-neutral-950);
  --primary-foreground: var(--aq-ref-neutral-50);
  --radius: var(--aq-ref-radius-2);

  --aq-sys-control-height: 2.25rem;
  --aq-sys-layer-overlay: 50;
  --aq-sys-shadow-overlay: 0 8px 24px rgb(0 0 0 / 0.15);
  --aq-sys-ease-standard: cubic-bezier(0.2, 0, 0, 1);

  /* Component roles */
  --aq-comp-button-radius: var(--radius);
  --aq-comp-slider-track-height: 0.25rem;
}

.dark {
  --background: var(--aq-ref-neutral-950);
  --foreground: var(--aq-ref-neutral-50);
  --primary: var(--aq-ref-neutral-50);
  --primary-foreground: var(--aq-ref-neutral-950);
}

@theme inline {
  --color-background: var(--background);
  --color-foreground: var(--foreground);
  --color-primary: var(--primary);
  --color-primary-foreground: var(--primary-foreground);

  --spacing-control: var(--aq-sys-control-height);
  --spacing-slider-track: var(--aq-comp-slider-track-height);
  --radius-button: var(--aq-comp-button-radius);
  --shadow-overlay: var(--aq-sys-shadow-overlay);
  --ease-standard: var(--aq-sys-ease-standard);

  --font-sans: var(--font-geist-sans, sans-serif);
  --text-control: 0.875rem;
  --text-control--line-height: 1.25rem;
}
```

This enables `h-control`, `h-slider-track`, `rounded-button`, `shadow-overlay`, `ease-standard`, and `text-control`.

Tailwind namespaces include `--spacing-*`, `--radius-*`, `--shadow-*`, `--font-*`, `--text-*`, `--font-weight-*`, `--leading-*`, `--tracking-*`, `--ease-*`, and `--animate-*`. `@theme` belongs at top level; theme-dependent aliases belong in selectors. Use `inline` when mapping aliases and `static` when all theme variables must be emitted. [Tailwind theme documentation](https://tailwindcss.com/docs/theme).

**Z-index and duration:** do not invent automatic `--z-index-*` or `--duration-*` theme namespaces. Use ordinary variables with:

```tsx
className="z-(--aq-sys-layer-overlay) duration-(--aq-ref-duration-fast)"
```

Or define named `@utility` rules. Motion tokens should also include reduced-motion behavior. [Z-index utilities](https://tailwindcss.com/docs/z-index), [duration utilities](https://tailwindcss.com/docs/transition-duration).

### Enforcement

Keep Ultracite/Biome. Its `useSortedClasses` rule sorts classes; it does not validate your token vocabulary or understand actual token values. [Biome rule limitations](https://biomejs.dev/linter/rules/use-sorted-classes/javascript/).

Recommended additional policy check:

- Inspect `className`, `cn`, and `cva` strings.
- Reject literal color values in TSX styles/classes.
- Reject arbitrary **design values** such as `p-[13px]`.
- Allow state/structural variants such as `data-[side=top]` and `[&>svg]`.
- Allow approved token references and calculations.
- Exempt genuinely dynamic geometry: slider percentages, knob angles, waveform coordinates.
- Use a reviewed allowlist for necessary one-offs.

A simple `rg` scan is useful for discovery, but a TS AST-based Bun script is safer for enforcement. A blanket ban on `[...]` would break legitimate shadcn selectors and accessibility-state styling.

`eslint-plugin-tailwindcss` **4.4.0** now declares Tailwind v4 support and provides `no-arbitrary-value`, disabled by default. Older repository-branch documentation still discusses beta support, so consult the published version. Adding ESLint solely for this policy is optional; a small custom check fits the existing lint stack better. [Published package](https://www.npmjs.com/package/eslint-plugin-tailwindcss/v/4.4.0).

### Optional Style Dictionary pipeline

If structured tokens become necessary:

```bash
bun add --cwd packages/ui --dev style-dictionary@5.7.0

bunx style-dictionary build \
  --config packages/ui/style-dictionary.config.mjs
```

Example config, with paths relative to the repository root from which that command runs:

```js
export default {
  usesDtcg: true,
  source: ["packages/ui/tokens/**/*.tokens.json"],
  platforms: {
    css: {
      transformGroup: "css",
      buildPath: "packages/ui/src/styles/generated/",
      files: [{
        destination: "tokens.css",
        format: "css/variables",
        options: { outputReferences: true }
      }]
    },
    js: {
      transformGroup: "js",
      buildPath: "packages/ui/src/tokens/generated/",
      files: [
        { destination: "tokens.js", format: "javascript/es6" },
        {
          destination: "tokens.d.ts",
          format: "typescript/es6-declarations"
        }
      ]
    }
  }
};
```

Keep a small handwritten Tailwind/shadcn alias bridge over the generated variables. Configure light/dark outputs deliberately; do not glob conflicting mode definitions into one platform.

Style Dictionary 5.7 requires **Node ≥22**. Bun can install it; use its Node CLI without forcing `--bun`. **UNVERIFIED:** execution under Bun’s runtime. [Configuration](https://styledictionary.com/reference/config/), [v5 requirements](https://styledictionary.com/versions/v5/migration/).

### Tailwind and theme configuration

`packages/ui/.storybook/main.ts`:

```ts
import type { StorybookConfig } from "@storybook/react-vite";
import tailwindcss from "@tailwindcss/vite";
```

Use a dedicated UI Storybook configuration rather than importing radio’s full TanStack/Cloudflare Vite configuration. [Vite builder](https://storybook.js.org/docs/builders/vite).

`packages/ui/.storybook/preview.tsx`:

```tsx
import type { Preview, Renderer } from "@storybook/react-vite";
import { withThemeByClassName } from "@storybook/addon-themes";
import { ThemeProvider } from "next-themes";
import "../src/styles/globals.css";

const preview: Preview = {
  tags: ["autodocs"],
  parameters: {
    a11y: { test: "error" }
  },
  decorators: [
    withThemeByClassName<Renderer>({
      themes: { light: "", dark: "dark" },
      defaultTheme: "light"
    }),
    (Story, context) => (
      <ThemeProvider
        attribute="class"
        enableSystem={false}
        forcedTheme={context.globals.theme === "dark" ? "dark" : "light"}
      >
        <Story />
      </ThemeProvider>
    )
  ]
};

export default preview;
```

The class decorator handles CSS-only components. The provider is additionally useful for components such as this repository’s Sonner wrapper that read `useTheme()`. Synchronize them to one selected theme. [Themes addon](https://storybook.js.org/docs/essentials/themes).

**Repository-specific source-path problem:** in `packages/ui/src/styles/globals.css`:

```css
@source "../../../apps/**/*.{ts,tsx}";
```

resolves to `packages/apps`, not root `apps`. The corresponding root-app path would be:

```css
@source "../../../../apps/**/*.{ts,tsx}";
```

Automatic detection may mask that mistake today. Prefer package-local scanning and app-owned app scanning before extraction.

Tailwind ignores `node_modules` by default; source paths are relative to the stylesheet, and dynamic class-name concatenation is not statically discoverable. Storybook source detection must cover `.stories.tsx`, MDX where relevant, and decorator classes. [Tailwind source detection](https://tailwindcss.com/docs/detecting-classes-in-source-files).

## D. Extracting `packages/ui` into a shared repository

### Distribution options

| Option | Advantages | Disadvantages / fit |
|---|---|---|
| **Versioned npm/GitHub package** | One implementation; semver; reproducible lockfiles; centrally shipped fixes and tokens | Requires releases and consumer upgrades. **Recommended default.** |
| **Private shadcn registry** | Consumers own/edit source; good for templates and product-specific compositions | Copies drift; fixes do not propagate automatically; updating customized files requires reconciliation |
| **Git submodule/subtree** | Source available in each checkout; commit-level pinning | More Git workflow overhead; dependency/build wiring remains; awkward multi-repo upgrades |
| **Bun link / git dependency** | Useful local iteration; little initial release setup | Links are machine-local; Git dependencies need commit/tag discipline and usable build artifacts; weaker release ergonomics |

Bun workspaces organize packages under a workspace root; `bun link` does not turn independent repositories into a shared, versioned workspace. Use linking for development, then test the packed artifact before release. [Bun link](https://bun.sh/docs/pm/cli/link).

**Recommendation:** publish components and tokens together initially as `@org/ui`. Add a registry later for app-owned page patterns or scaffolding. A copied registry item can itself depend on the versioned package.

A minimal registry example:

```json
{
  "$schema": "https://ui.shadcn.com/schema/registry.json",
  "name": "org",
  "homepage": "https://ui.example.com",
  "items": [{
    "name": "button",
    "type": "registry:ui",
    "files": [{
      "path": "src/components/button.tsx",
      "type": "registry:ui"
    }]
  }]
}
```

```bash
bunx --bun shadcn@4.22.1 build
```

Private consumer configuration:

```json
{
  "registries": {
    "@org": {
      "url": "https://ui.example.com/r/{name}.json",
      "headers": {
        "Authorization": "Bearer ${UI_REGISTRY_TOKEN}"
      }
    }
  }
}
```

```bash
bunx --bun shadcn@4.22.1 add @org/button
```

The domain/token names above are placeholders, not inferred infrastructure. [Registry build](https://ui.shadcn.com/docs/registry/getting-started), [registry authentication configuration](https://ui.shadcn.com/docs/components-json).

### Compiled JavaScript versus raw TSX

**Publish ESM JavaScript + declarations + CSS.** Use tsdown 0.23.1 for a new build pipeline. Raw TSX remains convenient inside the monorepo but transfers compilation requirements to every consumer.

Vite client compilation alone does not prove raw TSX will work in SSR: dependencies can be externalized and handed to a runtime without JSX transformation. A published package should also avoid relying on the parent repo’s TypeScript aliases and `@avoid.quest/config`. [tsdown](https://tsdown.dev/guide/), [React support](https://tsdown.dev/recipes/react-support).

Suggested build configuration in the extracted package:

```ts
import { defineConfig } from "tsdown";

export default defineConfig({
  entry: [
    "src/components/*.tsx",
    "src/hooks/*.ts",
    "src/lib/*.ts",
    "!src/**/*.stories.tsx",
    "!src/**/*.test.ts",
    "!src/**/*.test.tsx"
  ],
  root: "src",
  outDir: "dist",
  format: "esm",
  platform: "neutral",
  unbundle: true,
  dts: true,
  sourcemap: true,
  outExtensions: () => ({ js: ".js", dts: ".d.ts" }),
  copy: [
    { from: "src/styles", to: "dist/styles" },
    { from: "src/assets", to: "dist/assets" }
  ]
});
```

Keep React external, preserve necessary `"use client"` directives, and inspect the packed output. Dependencies declared in `dependencies`/`peerDependencies` should remain external rather than being duplicated into the UI bundle. [Entry configuration](https://tsdown.dev/options/entry), [output formats](https://tsdown.dev/options/output-format).

**UNVERIFIED:** this proposed config has not been built against the repository; asset imports, declaration portability, and directive preservation need artifact-level validation.

### Tailwind scanning and CSS shipping

There are two sound contracts.

**1. Consumer compiles Tailwind — recommended for these homogeneous apps.**

Ship tokens plus uncompiled Tailwind entry CSS. Consumers import it once:

```css
/* Example: consumer src/app.css */
@import "@org/ui/globals.css";
@source "../node_modules/@org/ui/dist";
@source "./";
```

That `node_modules` path is correct only when it is actually relative to this CSS file; hoisted monorepos may require a different path.

A more portable package can register its own output:

```css
/* Published dist/styles/globals.css */
@import "tailwindcss";
@import "tw-animate-css";
@import "./theme.css";

@source "../components";
```

Then consumer CSS only needs the import and its own source registration. Scanning compiled JS is valid because class strings remain visible.

**2. Package ships compiled component CSS.**

Consumers import the built stylesheet; they need not scan package component files. Trade-offs include larger fixed CSS, coordination with consumer Preflight/cascade layers, and deciding which token overrides remain supported. A token-only stylesheet is not sufficient—it does not contain component utility rules.

`@source inline("...")` safelists a finite set of literal utility classes. It is useful for controlled generated states, not a general replacement for scanning a library. [Tailwind source rules](https://tailwindcss.com/docs/detecting-classes-in-source-files).

Before extraction:

- Remove app-relative source globs from the library.
- Move radio-specific global presentation, such as the dark body gradient, into the app unless it is intentionally organization-wide.
- Provide font fallbacks and document font loading.
- Replace internal source aliases with relative imports or package-local imports that survive publication.

TypeScript project references are optional build-graph tooling inside a repository. Consumers of published declarations do **not** need references to the library’s source project. Adding references requires appropriate `composite`/declaration configuration; it is not required merely because the library becomes a package. [TypeScript project references](https://www.typescriptlang.org/docs/handbook/project-references.html).

### Versioning and release automation

Use **Changesets 3.0.3 with Action v2**, not examples mixing the new CLI with old Action v1 inputs:

```bash
bun add --dev @changesets/cli@3.0.3 tsdown@0.23.1
bunx changeset init
bunx changeset
```

A minimal workflow for the **extracted repository**, assuming its package is at the root and the scripts above exist:

```yaml
name: Release

on:
  push:
    branches: [main]

permissions:
  contents: write
  pull-requests: write

concurrency:
  group: release-${{ github.ref }}
  cancel-in-progress: false

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - uses: actions/setup-node@v7
        with:
          node-version: "24"
          registry-url: https://registry.npmjs.org/
          package-manager-cache: false

      - uses: oven-sh/setup-bun@v2
        with:
          bun-version: "1.4.2"

      - run: bun install --frozen-lockfile
      - run: bun run check
      - run: bun run typecheck
      - run: bun run build

      - uses: changesets/action@v2
        with:
          version-script: bun run version-packages
          publish-script: bun run release
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
```

This follows Changesets v3’s current `version-script` / `publish-script` input names. The secret is a required future configuration, not a credential verified in this task. Trusted publishing is another option; Changesets recommends separated actions when tightening publish permissions. [Current automation guide](https://changesets.dev/guide/automating), [Action inputs](https://github.com/changesets/action).

For **GitHub Packages**:

- Use the actual GitHub organization’s package scope.
- Set `publishConfig.registry` to `https://npm.pkg.github.com/`.
- Set the workflow registry URL accordingly.
- Add `packages: write` and use `NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}`.
- Grant consuming repositories package access; local installation generally needs a classic PAT with `read:packages`.
- Do not use `"private": true` to mean “private registry package”; that disables publication. [GitHub Packages authentication](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-npm-registry).

Treat removed props, changed callback semantics, and token removals as breaking changes. Significant visual/default-interaction changes also deserve explicit release notes even when TypeScript still compiles.

## Decisions I recommend

1. **Create Storybook baselines before migrating primitives.**
